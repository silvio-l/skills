# Persistent audit protocol

Python 3.10+, standard library. `schemas/run.schema.json` is the authoritative Draft 2020-12 data shape. The validator implements the exact subset used there (types, required/properties/additionalProperties, enum, bounds, arrays/uniqueness) and rejects unsupported schema keywords. It also checks cross-references and state transitions. There are no hidden package dependencies.

## State and baseline

`audit.db` (SQLite, standard library) contains immutable baseline metadata, content-hashed source manifest, profile, objects, units, evidence, findings, jobs, reviews, gaps and replayable history. `sequence` is optimistic concurrency control. Each write is one SQLite transaction under an exclusive `.write-lock`, so coordinator writes are never torn or interleaved. Read it only through `audit.py`; never edit the database directly (`check` detects rows that differ from the journal). Workers write separate fragments under `parts/`, never the ledger. Keep evidence and raw artifacts outside the audited repository.

`init RUN REPO --revision REV` refuses to overwrite a completed initialization. It inventories regular files without executing project code. Relevance policy (default for new runs, `scan_policy: 1`): Git metadata is always omitted; a directory is not traversed when it contains `.git` (nested checkout or worktree, its own baseline), when `git ls-files --others --ignored --exclude-standard --directory` reports it (read-only, fsmonitor disabled; no Git means no such skip) or when its name is a dependency/tool cache (`node_modules`, `.venv`, `__pycache__`, `.next`, `Pods`, `DerivedData` and similar; `GENERATED_DIRS` in `source_scan.py`). Ambiguous names such as `build/`, `dist/` or `target/` are skipped only when Git ignores them. Every skipped directory is recorded with its reason in `scan_ignored`, bound into the inventory digest and listed in the report; the run stays complete. The inventory review must dispute an entry that holds product source (for example a checked-in generated UI that is ignored); rerun `init --include PATH` on a new run. `--scan-all` restores the full traversal. Runs created before the policy keep scanning everything, so their drift baseline stays comparable. Bounded batches checkpoint to `scan-state.json` and continue automatically; rerun the same initialization after interruption to resume. Large files are hashed incrementally, not omitted by a size ceiling. The scanner reconciles source changes during discovery; a changed checkpoint is rejected and initialization must rerun on a stable baseline. Internal links to inventoried targets are fingerprinted without duplicate traversal. Unreadable paths and unresolved external/broken/excluded link targets remain explicit scan limits. Evidence/subruns cannot clear those immutable limits: establish an authorized self-contained baseline and start a linked run to close them. `--exclusions` intentionally narrows the scan and keeps the run incomplete; it is not the remedy for a full audit hitting a work-batch boundary. Never replace discovery with tracked files only. `drift` compares the observed manifest within the recorded scan scope, including additions/deletions. Source changes after initialization require a fresh linked run.

All tables are ID-keyed maps. Keep semantic object IDs (e.g. `O-checkout`, `O-settings`), stable criterion IDs from the catalogue, and stable unit IDs generated by `plan`. IDs must never be reused for a different object. The variant/criterion product is intentional: scope and non-applicability must be explicit. Empty screens still need applicable layout, language, state and navigation checks. A dynamic view with no standalone source file maps to its generator, configuration and entry registry.

Files: `decision` is pending/mapped/excluded/blocked. Map relevant files reciprocally to objects. Exclude only demonstrably irrelevant content with a reason; unavailable supported code is blocked. Objects: `label`, `kind` (view/flow/component/dialog/menu/notification/configuration/integration), `sources`, `variants`, `relations`, `audience`. A variant is an explicit readable combination, not an unexplained integer.

Profile values are strings with evidence IDs. Required keys: audience, tasks, platforms, states, entrypoints, runtime, scope, coordinator, tracker. `coordinator.value` is the real coordinator actor ID. `tracker.value` is the exact canonical tracker repository identifier (`owner/name`, or GitLab namespace/project), with evidence of destination discovery; the separate reviewed `tracker.json` holds provider/API endpoint/token variable/visibility. Runtime value names available and missing browser/native/AT capabilities. Scope distinguishes supported configurations from exercised ones.

## Matrix rules: applicability and equivalence

A large product multiplies objects × variants × 100 criteria into a matrix nobody can work through. Two optional tables make the reduction explicit instead of hiding it:

- `applicability` rows `{kinds, objects, criteria, dimensions, reason, evidence, actor}` declare combinations not applicable. A rule matches objects whose `kind` is in `kinds` and/or whose ID is in `objects` (both empty = every object), and criteria listed by ID or by catalogue `dimension` (at least one required). Example: window-resizing criteria (dimension `05`) for a fixed-size `dialog`.
- `equivalences` rows `{object, representative, variants, criteria, dimensions, reason, evidence, actor}` let the representative variant's unit stand for the member variants, for the named criteria/dimensions or (both empty) all criteria. A variant belongs to at most one class per object; the representative cannot be a member elsewhere.

Both need primary evidence (source, tokens, rendered comparison) and belong to the inventory digest, so the independent inventory review accepts or rejects them like any other inventory claim. `plan` creates only uncovered units and removes untouched pending units that a rule now covers (journalled as a deletion); it never removes worked units or units claimed by an active job. The report lists every rule and the number of covered units. A rule is a scope claim, not a pass: a disputed rule is resolved by inventory review, and per-unit exclusions remain available for individual cases.

Older ledgers without the rule tables stay readable; their inventory digest is unchanged until a rule is added.

## Ledger storage and scale

`apply` (and `patch`, `evidence`, `plan`) reads only the rows a fragment touches plus the rows that depend on them: the files and objects of a changed mapping, the units of a changed object, the jobs, findings, reviews and gaps that name a changed or removed unit. It enforces the same rules as the full validator for those rows and writes the result in one transaction, so a write stays well under a second even with 100,000 units (10–150 ms measured). `check` and `report` load the whole ledger and replay the complete journal, re-hash every evidence file and compare the source baseline; tampering between writes (a hand-edited row, a replaced evidence file) surfaces there, not at the next write. Run `check` before handing results on.

Runs created with the JSON ledger (`audit.json`) stay readable. The first write converts them after a full validation (`audit.py migrate RUN` does the same explicitly) and keeps the original as `audit.json.migrated`; an invalid JSON ledger is not converted.

## Transactions

A fragment has exactly this form (replace the sample values with observed facts):

```json
{
  "base_sequence": 0,
  "actor": "coordinator",
  "operations": [
    {"table": "profile", "id": "coordinator",
     "value": {"value": "coordinator", "evidence": ["E-context"]}}
  ]
}
```

Import evidence before referencing it; use the current sequence after import:

```sh
python3 "$SKILL/scripts/audit.py" evidence "$RUN" "$CAPTURE" \
  --id E-context --actor coordinator --kind document \
  --locator 'product brief, audience and scope' --environment 'revision and capture context'
python3 "$SKILL/scripts/audit.py" apply "$RUN" "$RUN/parts/profile.json"
```

`apply` rejects stale sequences, unknown fields, duplicates and invalid references atomically. Multiple mutually referring object/file rows belong in one fragment. On a stale merge, inspect changes and rebase the fragment deliberately; do not simply retry blindly. The journal preserves before/after rows. It detects accidental tampering, not a malicious actor rewriting the entire history. Actor labels are provenance assertions, not cryptographic identity verification.

`plan RUN --actor coordinator` creates pending units. Claim a job with `{owner, units, status:"active", reason}` under `jobs`. Order per unit: claim the job (as the owner actor) → unit `pending`→`running` → result → close the job as `done`. Operations apply in order, so all four may share one fragment as long as the job operation comes first and fragment actor, job owner and unit `actor` are the same ID; separate fragments work too.

`patch RUN --actor A --table T --id X` builds the operation from the current row and current sequence: `--set '{"label":"…"}'` replaces fields, `--add '{"sources":["…"]}'` unions list fields, `--append-variant V` adds an object variant (then run `plan`). `--fragment` writes the fragment to `parts/` instead of applying it. Use it instead of hand-merging rows; it keeps fields that changed since the row was last read. Units may be updated only by that owner while exactly one active job covers them. No automatic lease expiry can silently steal a live job. On interruption inspect the process/agent first; the original owner may cancel the job with a recovery reason, after which a new owner claims it. A stale filesystem lock likewise requires checking that no coordinator is running before removal. Completed work remains intact.

Unit transitions:

- pending → running, blocked or excluded
- running → pass, fail, blocked or excluded
- pass/fail/excluded → running (reopen before changing a terminal result)
- blocked → pending, running or excluded

Every row carries object, variant, criterion, status, actor, method, expected, actual, steps, evidence, limitations, reason. The generated pending row has empty observation fields. Pass/fail require actual method, steps, expected/actual and primary evidence. Exclusion/block requires evidence and reason. New blocked writes additionally require attempted steps, actual obstacle, limitations and a structured `blocker` object: `attempt`, `obstacle`, `alternatives`, `next_action`, `retry_when`, `context_digest` (all nonempty strings). Obtain the context digest with `next RUN`; it binds runtime/platform/scope profile evidence. Old rows remain readable but are reported unsubstantiated; changed runtime profiles mark previous blockers stale. Reassess them, then retry or return to pending under an owned job; remove obsolete blocker metadata while retaining journal history. See execution-loop.md for the semantic contract. Evidence cannot be fabricated to satisfy the gate. A successful test command with no asserted outcome is not evidence of usability.

Close jobs as done/cancelled only after reconciling all assigned units. Open jobs prevent completion. Screen-reader execution is excluded by default unless explicitly requested. Record the scope and evidence in `profile.scope`; follow M6 for the dedicated assistive-task unit and remaining criterion-level uncertainty. An exclusion describes audit scope, not product inapplicability. Do not count blocked, running, pending or excluded units as passes. Reports show these counts separately.

## Findings and independent review

Finding rows: title, units, status (suspected/confirmed/refuted), actor (original investigator), root_cause, impact, priority (P0–P3), steps, expected, actual, recommendation, evidence. Every finding has primary evidence and reproduction steps. A confirmed finding requires failing units. Refuted suspicions retain both the original observation and the counterevidence; revisit the unit's disposition rather than concealing a contradiction.

Review rows: actor, mode (`independent` or `separated`), scope (`inventory`, `unit`, `finding`, `final`), target (ID, or `all`), digest, verdict (`accept`, `reject`, `gap`), outcome, evidence, countercheck, limitations. Outcome is the reviewed unit status or finding disposition (`confirmed`/`refuted`); inventory/final use `none`. Reviews are append-only. `digest RUN --scope unit --target UNIT_ID` (or scope `finding`, `inventory`, `final`) prints the corresponding digest; inventory/final use target `all`. `digest RUN` retains the final-digest default. A reviewer may supply `{ "reviews": { "REVIEW_ID": REVIEW_ROW } }`; `wrap-reviews RUN DRAFT --actor REVIEWER` writes a uniquely named fragment in `parts/` and prints its path. It preserves reviewed content and rejects stale digests and actor mismatches; the coordinator then uses `apply`. The wrapper is format assistance, not review acceptance. Never blindly update a sequence or digest after changes. Do not use raw file hashes as review digests.

Finding workflow: investigator records suspected → independent reviewer reads raw evidence and records acceptance with intended outcome confirmed/refuted and a digest excluding only the mutable finding status → investigator promotes to that reviewed status. All other changes invalidate review. Unit reviews bind to the entire current row. Reviewer actor must differ from original investigator; actual isolation is enforced by the agent workflow, not inferred from labels.

Inventory review binds profile/files/objects/baseline, and must challenge missing objects/paths before accepting. Unit reviews cover every terminal unit, including exclusions and passes. Final review binds all substantive state, including jobs and evidence; add it last, after closing jobs. A subsequent substantive change invalidates it. Fresh raw evidence must be imported before calculating that final digest. An independent critic can cover a batch but must return explicit per-unit review rows and counterchecks; no blanket summary masquerading as individual inspection.

Negative reviews create gaps. Gap rows contain description (including review ID), status, units, evidence, resolution. Resolved gaps require new evidence and a resolution. Neither unresolved gaps nor an unresolved suspected finding can yield complete. A separated fallback review never satisfies independent acceptance.

## Outputs and meanings

`check` and `report` validate schema, replay, transitions, unit matrix, references, imported evidence hashes, baseline drift, open jobs/gaps, finding consistency and review freshness. Exit 0: FORMALLY_COMPLETE; 1: INCOMPLETE; 2: malformed input/tool failure. Mid-run exit 1 is expected. A confirmed product defect does not make the *audit* incomplete once it is fully substantiated and tracked. A schema or hash check cannot prove source truth, genuine human independence, empirical usability or semantic completeness.

`report` writes `result.json` and `report.md` from one snapshot, including the entire quality checklist, not just defects, plus `issue-export.json` (run, repository, revision, integrity, coverage notices, findings) as the input for `issues.py`; the full `result.json` of a large audit exceeds the adapter's input bound. Publish issue receipts separately through `issues.py`; report both audit completion and delivery status. A complete audit with a failed tracker write is still unfinished issue delivery. See [issues.md](issues.md).


## Bounded discovery and practical continuation

`init RUN REPOSITORY --revision REV --exclusions exclusions.json` accepts an explicit path-to-reason map, for example `{ ".claude/worktrees": "Separate nested checkouts; not examined in this run" }`. Canonical relative paths match exact files/subtrees. These exclusions are separate from the relevance policy above: policy skips are not product source and keep the run complete, while `--exclusions` omits product source and keeps it incomplete. Untracked files that Git does not ignore are always scanned. Omitted paths are retained in the baseline and inventory digest. Drift checks cover the included manifest only. **Every such run remains INCOMPLETE**, even if all included units are finished: omitted content has not been independently established irrelevant. No automatic promotion or coverage federation is provided. Use a fresh full run for a complete claim. Keep a parent/child manifest with run IDs, baselines, paths and unresolved relationships as evidence when dividing discovery; a tracked-only copy cannot stand in for a complete working tree.

`check` and `report` print grouped errors with counts and up to three examples per cause; the full list is always written to `validation.json`. Use `--verbose` only when full terminal output is needed. `report` still writes the full checklist and structured result. `resume RUN --object OBJECT_ID --status blocked --limit 20` selects bounded work with its owning jobs; omit filters to list pending/running/blocked units. Maximum limit is 100. Inspect limitations and raw sources before changing status: unavailable runtime does not automatically block source-verifiable criteria.

Finding output separates `independent_confirmation` (a current independent finding review exists) from `independent_validated` (integrity and publication blockers also pass). Publication rule, unambiguous:

- Inventory review `gap` = coverage notice. Objects or paths are missing, which does not contradict a finding confirmed on its own evidence. It appears in `coverage_notices`, the report and every issue body ("audit coverage incomplete"), and still keeps the audit INCOMPLETE until resolved.
- Inventory review `reject`, final review `reject`/`gap`, and unit/finding reviews `reject`/`gap` on the finding's own units are `publication_blockers`.

Local objections should be recorded by the independent reviewer as unit/finding reviews when primary evidence supports that boundary. Do not downgrade an existing objection to publish a finding; resolve it with evidence.

## Work selection

`next RUN --limit 12` is read-only and returns current context digest, documented/stale/unsubstantiated blocker counts, bounded unit packages for every object/variant/action, outstanding reviews and active job ownership. Packages do not grant a job lease or establish a safe runtime. Continue until requested work is done; a package boundary or report does not authorize stopping. Independent reviews are requested for terminal units, not thousands of untouched pending rows.
