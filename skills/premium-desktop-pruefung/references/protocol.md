# Persistent audit protocol

Python 3.10+, standard library. `schemas/run.schema.json` is the authoritative Draft 2020-12 data shape. The validator implements the exact subset used there (types, required/properties/additionalProperties, enum, bounds, arrays/uniqueness) and rejects unsupported schema keywords. It also checks cross-references and state transitions. There are no hidden package dependencies.

## State and baseline

`audit.db` (SQLite, standard library) contains immutable baseline metadata, content-hashed source manifest, profile, objects, units, evidence, findings, jobs, reviews, gaps and replayable history. `sequence` is optimistic concurrency control. Each write is one SQLite transaction under an exclusive `.write-lock`, so coordinator writes are never torn or interleaved. Read it only through `audit.py`; never edit the database directly (`check` detects rows that differ from the journal). Workers write separate fragments under `parts/`, never the ledger. Keep evidence and raw artifacts outside the audited repository.

`init RUN REPO --revision REV` refuses to overwrite a completed initialization. It inventories regular files without executing project code. Relevance policy (default for new runs, `scan_policy: 1`): Git metadata is always omitted; a directory is not traversed when it contains `.git` (nested checkout or worktree, its own baseline), when `git ls-files --others --ignored --exclude-standard --directory` reports it (read-only, fsmonitor disabled; no Git means no such skip) or when its name is a dependency/tool cache (`node_modules`, `.venv`, `__pycache__`, `.next`, `Pods`, `DerivedData` and similar; `GENERATED_DIRS` in `source_scan.py`). Ambiguous names such as `build/`, `dist/` or `target/` are skipped only when Git ignores them. Every skipped directory is recorded with its reason in `scan_ignored`, bound into the inventory digest and listed in the report; the run stays complete. The inventory review must dispute an entry that holds product source (for example a checked-in generated UI that is ignored); rerun `init --include PATH` on a new run. `--scan-all` restores the full traversal. Runs created before the policy keep scanning everything, so their drift baseline stays comparable. `relocate RUN NEW_PATH [--copy-missing]` points a run at another checkout of the same baseline (for example a pinned worktree after a background `git pull` moved the original) only if NEW_PATH reproduces the compared baseline exactly; see [execution-loop.md](execution-loop.md). `adopt-scan-policy RUN [--include PATH]` switches such a run to the policy without rewriting its journal: it refuses unless every row in the newly skipped directories is an excluded file (it names the directories to `--include` otherwise; an include covers its whole subtree) and the policy scan reproduces the remaining baseline exactly. Rows in skipped directories stay in the ledger but are no longer compared by `drift`/`check`; the change is recorded in `scan_policy_adopted`, makes outstanding fragments stale and invalidates the inventory review, which must be repeated against the not-inventoried list. Bounded batches checkpoint to `scan-state.json` and continue automatically; rerun the same initialization after interruption to resume. Large files are hashed incrementally, not omitted by a size ceiling. The scanner reconciles source changes during discovery; a changed checkpoint is rejected and initialization must rerun on a stable baseline. Internal links to inventoried targets are fingerprinted without duplicate traversal. Unreadable paths and unresolved external/broken/excluded link targets remain explicit scan limits. Evidence/subruns cannot clear those immutable limits: establish an authorized self-contained baseline and start a linked run to close them. `--exclusions` intentionally narrows the scan and keeps the run incomplete; it is not the remedy for a full audit hitting a work-batch boundary. Never replace discovery with tracked files only. `drift` compares the observed manifest within the recorded scan scope, including additions/deletions. Source changes after initialization require a fresh linked run.

All tables are ID-keyed maps. Keep semantic object IDs (e.g. `O-checkout`, `O-settings`), stable criterion IDs from the catalogue, and stable unit IDs generated by `plan`. IDs must never be reused for a different object. The variant/criterion product is intentional: scope and non-applicability must be explicit. Empty screens still need applicable layout, language, state and navigation checks. A dynamic view with no standalone source file maps to its generator, configuration and entry registry.

Files: `decision` is pending/mapped/excluded/blocked. Map relevant files reciprocally to objects; a files operation may omit `sha256` (`apply` copies the immutable manifest hash), so a new object and its file mappings go into one fragment without reading the manifest first, or `classify --prefix PATH --map OBJECT` maps a directory or a single file to an existing object. Exclude only demonstrably irrelevant content with a reason; unavailable supported code is blocked. Objects: `label`, `kind` (view/flow/component/dialog/menu/notification/configuration/integration), `sources`, `variants`, `relations`, `audience`. A variant is an explicit readable combination, not an unexplained integer.

Profile values are strings with evidence IDs. Required keys: audience, tasks, platforms, states, entrypoints, runtime, scope, coordinator, tracker. `coordinator.value` is the real coordinator actor ID. `tracker.value` is the exact canonical tracker repository identifier (`owner/name`, or GitLab namespace/project), with evidence of destination discovery; the separate reviewed `tracker.json` holds provider/API endpoint/token variable/visibility. Runtime value names available and missing browser/native/AT capabilities. Scope distinguishes supported configurations from exercised ones.

## Matrix rules: applicability and equivalence

A large product multiplies objects × variants × 100 criteria into a matrix nobody can work through. Two optional tables make the reduction explicit instead of hiding it:

- `applicability` rows `{kinds, objects, criteria, dimensions, reason, evidence, actor}` declare combinations not applicable. A rule matches objects whose `kind` is in `kinds` and/or whose ID is in `objects` (both empty = every object), and criteria listed by ID or by catalogue `dimension` (at least one required). Optional `variants` limits the rule to those variant names (empty or absent = all variants). Example: window-resizing criteria (dimension `05`) for a fixed-size `dialog`. A rule states that criteria cannot apply, with evidence; it is never a scope cut. A narrower audit scope is recorded in `profile.scope` and leaves the uncovered units pending, so the run reports them instead of passing.
- `equivalences` rows `{object, representative, variants, criteria, dimensions, reason, evidence, actor}` let the representative variant's unit stand for the member variants, for the named criteria/dimensions or (both empty) all criteria. A variant belongs to at most one class per object; the representative cannot be a member elsewhere.

Both need primary evidence (source, tokens, rendered comparison) and belong to the inventory digest, so the independent inventory review accepts or rejects them like any other inventory claim. `plan` creates only uncovered units and removes untouched pending units that a rule now covers (journalled as a deletion); it never removes worked units or units claimed by an active job. The report lists every rule and the number of covered units. A rule is a scope claim, not a pass: a disputed rule is resolved by inventory review, and per-unit exclusions remain available for individual cases.

Retire a rule with an operation whose `value` is `null` (journaled; the inventory digest changes, so the inventory review repeats), then run `plan`, which recreates the units the rule covered. Never reuse a rule ID for a different scope. `plan` prints `{sequence, created, pruned, covered_by_rule, units}`.

`inventory RUN` prints a compact inventory for reviewers without the file manifest: objects with variants, relations and the planned criterion count per dimension and variant, every rule with its variants and covered-unit count, file decision counts, the not-inventoried list and the inventory digest. Its `warnings` flag equivalences whose variants differ in size, layout or mode tokens (`compact`/`wide`, `dark`/`light`, `rtl`, …); structure, navigation and setting criteria rarely carry across such variants, so the rule needs explicit evidence or narrower criteria. Critics review against these rows, not against prose describing the rules.

`classify RUN --actor A --prefix DIR --exclude REASON` (or `--map OBJECT`) decides every inventoried file under one directory in a single write; it refuses to exclude files that are mapped to objects, and `--map` also adds the files to the object's sources.

Older ledgers without the rule tables stay readable; their inventory digest is unchanged until a rule is added.

## Ledger storage and scale

`apply` (and `patch`, `evidence`, `plan`) reads only the rows a fragment touches plus the rows that depend on them: the files and objects of a changed mapping, the units of a changed object, the jobs, findings, reviews and gaps that name a changed or removed unit. It enforces the same rules as the full validator for those rows and writes the result in one transaction, so a write stays well under a second even with 100,000 units (10–150 ms measured). `check` and `report` load the whole ledger and replay the complete journal, re-hash every evidence file and compare the source baseline; tampering between writes (a hand-edited row, a replaced evidence file) surfaces there, not at the next write. Run `check` before handing results on.

Runs created with the JSON ledger (`audit.json`) stay readable. The first write converts them after a full validation (`audit.py migrate RUN` does the same explicitly) and keeps the original as `audit.json.migrated`; an invalid JSON ledger is not converted.

## Transactions

A fragment has exactly this form (replace the sample values with observed facts):

```json
{
  "base_sequence": 0,
  "actor": "coordinator",
  "operations": [
    {"table": "profile", "id": "coordinator",
     "value": {"value": "coordinator", "evidence": ["E-context"]}}
  ]
}
```

Import evidence before referencing it; use the current sequence after import (`apply`, `evidence` and `patch` print `{"sequence": N}`; a rebased `apply` adds `rebased_from`). Evidence `kind` is one of `source`, `runtime`, `screenshot`, `trace`, `test`, `document`; a measurement is `runtime` (or `trace` for collector output). `evidence` accepts a directory too: every file is stored content-addressed and the evidence row points at a hash manifest (`members`: relative name → SHA-256), which `check` verifies member by member. Symlinks, special files and empty directories are refused. `evidence RUN BATCH.json --batch --actor A` registers many artifacts (`[{id, source, kind, locator, environment}]`, sources relative to the batch file) in one write instead of one process per file:

```sh
python3 "$SKILL/scripts/audit.py" evidence "$RUN" "$CAPTURE" \
  --id E-context --actor coordinator --kind document \
  --locator 'product brief, audience and scope' --environment 'revision and capture context'
python3 "$SKILL/scripts/audit.py" apply "$RUN" "$RUN/parts/profile.json"
```

`apply` rejects unknown fields, duplicates and invalid references atomically. Multiple mutually referring object/file rows belong in one fragment. A fragment whose `base_sequence` is older than the ledger is **rebased** when no row it writes (table and ID) changed since its base: parallel workers on disjoint units no longer collide, and the result is validated against the current ledger like any write. When a written row did change, `apply` names the rows; rebuild those operations from the current state, never retry blindly. Ledgers written before this rule gain rebase marks on their next write; older positions stay strict. [fragments.md](fragments.md) has a complete, schema-checked example for every table. The journal preserves before/after rows. It detects accidental tampering, not a malicious actor rewriting the entire history. Actor labels are provenance assertions, not cryptographic identity verification.

`plan RUN --actor coordinator` creates pending units. Claim a job with `{owner, units, status:"active", reason}` under `jobs`; the coordinator decides the package, the worker writes the claim as the owner actor (a job owned by someone else cannot be written). `next` lists each package's units with their criteria (`criteria`). Order per unit: claim the job (as the owner actor) → unit `pending`→`running` → result → close the job as `done`. Operations apply in order, so all four may share one fragment as long as the job operation comes first and fragment actor, job owner and unit `actor` are the same ID; separate fragments work too. **Rework is a claim too:** a terminal unit that a worker decides again (reopen → new result) must be listed in that worker's job; put every rework unit into the job when dispatching it.

`ingest RUN RESULT.json --actor WORKER` imports one worker result in a single write into a job the worker has already claimed (ingest closes a job, it never claims one): `{"job", "evidence": [batch items, sources relative to the result file], "units": {UNIT: {status, method, expected, actual, steps, evidence, limitations, reason, blocker?, finding?}}, "findings": {ID: row without actor}, "close": true}`. It moves each unit through `running` to its terminal status, refuses units outside the job, adds a unit to the finding named in its `finding` field (new in this result or existing) and closes the job when `close` is set. A confirmed finding that gains units drops back to `suspected` and needs a new review; the output lists every touched finding. Re-deciding a terminal unit (rework after a rejected review) needs a new claimed job; a unit that leaves `blocked` loses its blocker record. To take a unit out of a finding, `patch` the finding's `units` first, then rework the unit.

`show RUN --table T --id X [--id Y]` prints current rows read-only (findings with their units, objects with relations, files with their decision and reason) without loading the ledger; use it instead of reading `audit.db`. Without `--id` it lists the table's IDs with their status or verdict, and `--object O` narrows units, findings, jobs, gaps, files and reviews to one object. The investigator promotes a reviewed finding with `patch RUN --actor INVESTIGATOR --table findings --id F --set '{"status":"confirmed"}'`. `patch RUN --actor A --table T --id X` builds the operation from the current row and current sequence: `--set '{"label":"…"}'` replaces fields, `--add '{"sources":["…"]}'` unions list fields, `--append-variant V` adds an object variant (then run `plan`). `--fragment` writes the fragment to `parts/` instead of applying it. Use it instead of hand-merging rows; it keeps fields that changed since the row was last read. Units may be updated only by that owner while exactly one active job covers them. No automatic lease expiry can silently steal a live job. On interruption inspect the process/agent first; the original owner may cancel the job with a recovery reason, after which a new owner claims it. A stale filesystem lock likewise requires checking that no coordinator is running before removal. Completed work remains intact.

Unit transitions:

- pending → running, blocked or excluded
- running → pass, fail, blocked or excluded
- pass/fail/excluded → running (reopen before changing a terminal result)
- blocked → pending, running or excluded

Every row carries object, variant, criterion, status, actor, method, expected, actual, steps, evidence, limitations, reason. The generated pending row has empty observation fields. Pass/fail require actual method, steps, expected/actual and primary evidence. Exclusion/block requires evidence and reason. New blocked writes additionally require attempted steps, actual obstacle, limitations and a structured `blocker` object: `attempt`, `obstacle`, `alternatives`, `next_action`, `retry_when`, `context_digest` (all nonempty strings). `apply` normalizes the shapes workers naturally send: a list of `alternatives` is joined with `; `, a missing `actual` takes `blocker.obstacle`, a missing `context_digest` takes the current one (`next RUN` prints it; a rebased fragment is refused instead when runtime, platforms or scope changed since its base); the error names any field still missing. The context digest binds runtime/platform/scope profile evidence. Old rows remain readable but are reported unsubstantiated; changed runtime profiles mark previous blockers stale. Reassess them, then retry or return to pending under an owned job; remove obsolete blocker metadata while retaining journal history. See execution-loop.md for the semantic contract. Evidence cannot be fabricated to satisfy the gate. A successful test command with no asserted outcome is not evidence of usability.

Close jobs as done/cancelled only after reconciling all assigned units. Open jobs prevent completion. Screen-reader execution is excluded by default unless explicitly requested. Record the scope and evidence in `profile.scope`; follow M6 for the dedicated assistive-task unit and remaining criterion-level uncertainty. **Which status for work that is not a pass or fail.** `excluded` carries two dispositions, and its reason names which: a *scope cut*, where the method is outside what the audit was authorised to do (screen-reader execution by default, empirical user research when the brief names no study or participants), recorded in `profile.scope` with the request as evidence and the reason starting `Scope cut:`; or *not applicable*, where a product fact makes the criterion impossible to trigger on this object (no media, no form, no time limit), with the reason starting `Not applicable:` and source or runtime evidence (when many objects share the fact, propose an `applicability` rule instead). `blocked` is only for authorised work obstructed on this host (a missing permission, an unreachable state), with a blocker record; a scope change is not a blocker. Work that simply was not done stays `pending`: a user-requested partial audit leaves the units it does not cover pending rather than excluding them. An exclusion never claims the product conforms. Do not count blocked, running, pending or excluded units as passes. Reports show these counts separately.

## Findings and independent review

Finding rows: title, units, status (suspected/confirmed/refuted/duplicate), actor (original investigator), root_cause, impact, priority (P0–P3), steps, expected, actual, recommendation, evidence; optional `duplicate_of` and `tracking`. Every finding has primary evidence and reproduction steps. A confirmed finding requires failing units; a suspected one may start without units (a cross-cutting or design question) and gains them before confirmation. Refuted suspicions retain both the original observation and the counterevidence; revisit the unit's disposition rather than concealing a contradiction.

Only the investigator changes a finding's content. Anyone may add units (a confirmed finding that gains units returns to `suspected`), propose or mark a duplicate, or apply reviewer corrections (below). A **duplicate** is a claim like a confirmation and needs its own independent review: set `duplicate_of` on the suspected finding (a proposal naming a primary that is not itself a duplicate), let a critic accept it with outcome `duplicate`, then set `status: "duplicate"`. A critic who spots a duplicate first records a `gap` review naming the primary; the coordinator or the author sets `duplicate_of`, the critic accepts with outcome `duplicate` on the new digest, the author marks it, and `resolve-answered` closes the gap review. `duplicate_of` is part of the review digest; status is not, so the promotion keeps the review valid, while re-pointing or adding units invalidates it (a duplicate that gains units returns to `suspected`). Only then do its units count for a confirmed primary (a failing unit listed only in that duplicate is covered), and `issues.py` merges it into the primary's issue with the primary's title and text. `tracking` `{kind, reference, reason, evidence}` records that the defect is already tracked (`kind: "issue"`, reference `#N` or an issue URL; publication links it and verifies the issue exists instead of creating one) or was fixed after the baseline (`kind: "fixed"`, reference a commit or release; not published). It is part of the reviewed content.

Review rows: actor, mode (`independent` or `separated`), scope (`inventory`, `unit`, `finding`, `final`), target (ID, or `all`), digest, verdict (`accept`, `reject`, `gap`), outcome, evidence, countercheck, limitations; optional `corrections` and `base_digest`. Outcome is the reviewed unit status (`pass`/`fail`/`excluded`/`blocked`) or finding disposition (`confirmed`/`refuted`, or `duplicate`); inventory/final use `none`. Reviews are append-only. `digest RUN --scope unit --target UNIT_ID` (or scope `finding`, `inventory`, `final`) prints the corresponding digest; inventory/final use target `all`. `digest RUN --scope unit --targets U1,U2` or `--targets-file IDS` prints a JSON map for a whole batch in one process. `digest RUN` retains the final-digest default. The plain `--target` digest of a finding or unit is also the `base_digest` of a correcting review. To find the terminal units to review, use `resume RUN --status pass` (or `fail`, `excluded`, `blocked`); `next` lists only a bounded sample.

**Corrections instead of another review round.** A critic who accepts a unit or finding subject to precise text fixes writes them machine-readably: `corrections` `{field: new value}` (existing text fields only; never `status`, `actor`, identity fields, `duplicate_of`, `units`, `evidence`, `root_cause`, `tracking` or `blocker`, which change what the finding is and stay with its author), `base_digest` = digest of the row as read, and `digest` = digest of the row *with the corrections applied*; `digest RUN --scope finding --target F --corrections JSON` prints both. `apply-corrections RUN --actor COORDINATOR [--review ID]` writes every such correction whose target still has `base_digest` (a unit only once its result is final and equals the review outcome; running work stays with the job owner); the review then accepts the corrected row, so no further critic is needed. A target that changed meanwhile is skipped with the reason. `apply` accepts a third-party write to a finding or unit only when it is exactly such a correction.

`resolve-answered RUN --actor COORDINATOR` resolves every `reject`/`gap` review whose target was reworked and then independently accepted on its current content, writing a gap `G-answered-<review>` that names the answering review as evidence. For a finding the accepting review counts once its outcome is the finding's status, so run it after the author's promotion (or duplicate marking). A reviewer may supply `{ "reviews": { "REVIEW_ID": REVIEW_ROW } }`; `wrap-reviews RUN DRAFT --actor REVIEWER` writes a uniquely named fragment in `parts/` and prints its path. It preserves reviewed content and rejects stale digests and actor mismatches; the reviewer (or the coordinator) then applies the fragment with `apply`, whose actor is the reviewer named in it. The wrapper is format assistance, not review acceptance. Never blindly update a sequence or digest after changes. Do not use raw file hashes as review digests.

Finding workflow: investigator records suspected → independent reviewer reads raw evidence and records acceptance with intended outcome confirmed/refuted and a digest excluding only the mutable finding status → investigator promotes to that reviewed status. All other changes invalidate review. Unit reviews bind to the entire current row. Reviewer actor must differ from original investigator; actual isolation is enforced by the agent workflow, not inferred from labels.

Inventory review binds profile/files/objects/baseline, and must challenge missing objects/paths before accepting. Missing objects or paths are a `gap`; a wrong or unevidenced profile statement, variant or relation is a `reject`, which the coordinator fixes before requesting a fresh review. A later profile change (for example a new scope cut) makes the accepted inventory review stale. Unit reviews cover every terminal unit, including exclusions and passes. Final review binds all substantive state, including jobs and evidence; add it last, after closing jobs. A subsequent substantive change invalidates it. Fresh raw evidence must be imported before calculating that final digest. An independent critic can cover a batch but must return explicit per-unit review rows and counterchecks; no blanket summary masquerading as individual inspection.

Negative reviews create gaps. Gap rows contain description (including review ID), status, units, evidence, resolution, and an optional `category`: `foreign-change` records activity outside the audit on the test host (another session's build, remote provisioning, an update) with the affected units; the report lists those in their own section. Resolved gaps require new evidence and a resolution. Neither unresolved gaps nor an unresolved suspected finding can yield complete. A separated fallback review never satisfies independent acceptance.

## Outputs and meanings

`check` and `report` validate schema, replay, transitions, unit matrix, references, imported evidence hashes, baseline drift, open jobs/gaps, finding consistency and review freshness. Exit 0: FORMALLY_COMPLETE; 1: INCOMPLETE; 2: malformed input/tool failure. Mid-run exit 1 is expected. A confirmed product defect does not make the *audit* incomplete once it is fully substantiated and tracked. A schema or hash check cannot prove source truth, genuine human independence, empirical usability or semantic completeness.

`report` writes `result.json` and `report.md` from one snapshot, including the entire quality checklist, not just defects, plus `issue-export.json` (run, repository, revision, integrity, coverage notices, findings) as the input for `issues.py`; the full `result.json` of a large audit exceeds the adapter's input bound. Publish issue receipts separately through `issues.py`; report both audit completion and delivery status. A complete audit with a failed tracker write is still unfinished issue delivery. See [issues.md](issues.md).


## Bounded discovery and practical continuation

`init RUN REPOSITORY --revision REV --exclusions exclusions.json` accepts an explicit path-to-reason map, for example `{ ".claude/worktrees": "Separate nested checkouts; not examined in this run" }`. Canonical relative paths match exact files/subtrees. These exclusions are separate from the relevance policy above: policy skips are not product source and keep the run complete, while `--exclusions` omits product source and keeps it incomplete. Untracked files that Git does not ignore are always scanned. Omitted paths are retained in the baseline and inventory digest. Drift checks cover the included manifest only. **Every such run remains INCOMPLETE**, even if all included units are finished: omitted content has not been independently established irrelevant. No automatic promotion or coverage federation is provided. Use a fresh full run for a complete claim. Keep a parent/child manifest with run IDs, baselines, paths and unresolved relationships as evidence when dividing discovery; a tracked-only copy cannot stand in for a complete working tree.

`check` and `report` print grouped errors with counts and up to three examples per cause; the full list is always written to `validation.json`. Use `--verbose` only when full terminal output is needed. `report` still writes the full checklist and structured result. `resume RUN --object OBJECT_ID --status blocked --limit 20` selects bounded work with its owning jobs; omit filters to list pending/running/blocked units. Maximum limit is 100. Inspect limitations and raw sources before changing status: unavailable runtime does not automatically block source-verifiable criteria.

Finding output separates `independent_confirmation` (a current independent finding review exists) from `independent_validated` (integrity and publication blockers also pass). Publication rule, unambiguous:

- Inventory review `gap` = coverage notice. Objects or paths are missing, which does not contradict a finding confirmed on its own evidence. It appears in `coverage_notices`, the report and every issue body ("audit coverage incomplete"), and still keeps the audit INCOMPLETE until resolved.
- Inventory review `reject`, final review `reject`/`gap`, and unit/finding reviews `reject`/`gap` on the finding's own units are `publication_blockers`.

Local objections should be recorded by the independent reviewer as unit/finding reviews when primary evidence supports that boundary. Do not downgrade an existing objection to publish a finding; resolve it with evidence.

## Work selection

`next RUN --limit 12 [--first OBJECT ...]` is read-only and returns current context digest, documented/stale/unsubstantiated blocker counts, bounded unit packages for every object/variant/action, outstanding reviews and active job ownership. Packages do not grant a job lease or establish a safe runtime. Continue until requested work is done; a package boundary or report does not authorize stopping. Independent reviews are requested for terminal units, not thousands of untouched pending rows. A matrix of thousands of units is not worked in one session: order it by risk with `--first` (repeatable, e.g. the primary task flow, then data-loss and permission dialogs) so packages for those objects come first; every object still gets its package.
