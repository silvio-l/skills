# Research basis and limits

Reviewed 2026-11-18. This register distinguishes normative requirements, informative platform guidance, research and the skill's own operational synthesis. Linked documents may change: record the version actually applied during an audit. No proprietary ISO text was obtained or claimed to have been read.

| Source and inspected edition | Status and use | Limits |
| --- | --- | --- |
| [WCAG 2.2, Recommendation 12 December 2024](https://www.w3.org/TR/2024/REC-WCAG22-20241212/) | Normative web accessibility baseline. `criteria.json` maps all 55 A/AA success criteria individually to official Understanding pages; AAA is outside the required baseline. | Full criterion definitions, exceptions, conformance requirements and complete processes govern judgments. Parsing 4.1.1 was removed in WCAG 2.2 and is not reinstated here. Source/code-only analysis cannot establish conformance. |
| [WCAG2ICT 2.2, Group Note 11 December 2025](https://www.w3.org/TR/2025/NOTE-wcag2ict-22-20251211/) | Informative interpretation for non-web software/documents, including desktop and closed functionality. | Not a separate normative conformance standard. Record applicability and native adaptation, and account for OS accessibility services and platform constraints. |
| [WAI ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/) | Widget keyboard, roles, states and interaction reference; use to construct counterchecks for custom web controls. | Informative patterns, not a substitute for normative ARIA/HTML or a universal requirement that every control resemble an APG example. Prefer native semantics when appropriate. |
| [WAI evaluation methodology overview](https://www.w3.org/WAI/test-evaluate/conformance/wcag-em/) | Scope, exploration, evaluation and reporting discipline, plus involvement of users. | Its representative sampling principles do not prove the user's requested whole-repository coverage. This skill adds explicit unit/variant reconciliation and leaves untested areas visible. |
| [WAI selecting evaluation tools](https://www.w3.org/WAI/test-evaluate/tools/selecting/) | Supports combining automated and manual examination. | Tool results alone cannot decide every accessibility requirement. Missing manual evidence remains missing. |
| [ISO 9241-11:2018 public abstract](https://www.iso.org/standard/63500.html) | Context-dependent effectiveness, efficiency and satisfaction inform task-centered evaluation. | Public abstract only; no claim to have audited the complete paid standard or certified compliance. |
| [Nielsen's ten usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | Author's original heuristic framework, reviewed 2024: feedback, task language, control, consistency, errors, recognition and simplicity. | Heuristics organize expert judgment; they are not measured user outcomes or a numerical quality scale. |
| [Sweller, Cognitive Load During Problem Solving (1988), DOI](https://doi.org/10.1207/s15516709cog1202_4) | Original research reference for considering avoidable working-memory demand; bibliographic/abstract-level consultation. | Learning/problem-solving theory does not supply a universal UI density limit, click count or measurement of a specific user's cognitive load. No full-paper experiment is represented as replicated. |
| [NASA Task Load Index](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/) | Primary source for a subjective workload instrument; suitable when real participants and an explicit protocol are available. | An AI cannot fill in participant responses. Instrument results do not establish accessibility or universal product superiority. |
| [Apple HIG accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility.md) | Native platform considerations, system settings, alternatives and accessibility inspection inform desktop adaptation. | Platform recommendations and point units must not silently replace WCAG CSS-pixel definitions or normative contrast rules. No general requirement for one visual style. |
| [Microsoft Windows accessibility overview](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-overview) | UI Automation, keyboard/AT integration and user customization inform native tests. | Framework support does not establish correct application semantics or successful screen-reader tasks. |
| [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing) | Official implementation guidance for browser automation and optional axe integration. Useful for state-specific scans and reproducible actions. | Browser tooling is conditional on installation and safe runtime access; it does not inspect arbitrary native desktop controls. Automated scans explicitly require manual supplementation. |

The official [contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and [target sizing](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) explanations were also consulted to avoid common numerical misinterpretations. Their thresholds are criterion-specific, unlike invented universal rules for whitespace or premium appearance.

## Original method design

The 45 non-WCAG criteria are this skill's synthesis, not quotations or independently standardized requirements. Their individual methods, pass conditions and counterchecks operationalize the 12 requested dimensions. Objective observations (clipped text, failed transition, lost value) are separated from audience-dependent judgments (discoverability, visual calm, confidence). Actual audience perception requires participant evidence; absent that, it remains a reasoned hypothesis. Simplicity outranks decoration, but useful professional information density is not automatically a defect.

M1 connects implementation and visible behavior; M2 tests recognition and task continuity; M3 makes visual claims comparable; M4 exercises failure chains; M5 covers adaptation boundaries; M6 combines normative, automated and assistive evidence; M7 preserves the distinction between empirical and expert evidence; M8 actively falsifies; M9 retains desktop-specific daily work, first use and settings behavior. Methods require both success and counterexamples, and allow justified exceptions rather than absolute design fashions.

The predecessor `premium-desktop-pruefung` supplied useful concrete methods for real-window evidence, first reusable result, permission denial, interruptions, retained selection/focus, monitor changes, settings search, persistence, scopes and unavailable resources. These were retained and generalized in the DES/ON/SET criteria. Its five visual examples and trend articles are inspiration, not an empirical premium standard; they do not justify mandatory sidebars, accents, native-only rendering, competitor downloads or image generation. Its correction/build instructions are superseded by audit-only issue handoff. Existing app technology is examined as found.

## Tool and evidence selection

Use already-available browser automation for web interactions and screenshot comparisons, an automated accessibility engine for its supported rules, and actual VoiceOver/NVDA/Narrator or supported target AT for task evidence. For native controls, use platform accessibility inspection/UI Automation and actual window/input operation; DOM screenshots of a surrogate web implementation are not native evidence. Record versions and capabilities rather than assume tools exist on both assistant platforms.

Source analysis is portable and safe when treated as untrusted data. Application execution requires a controlled test environment. Automated image comparison detects change, not whether the change improves usability. Accessibility trees describe exposed semantics, not what a screen reader actually announced. A design-system token inventory detects divergence, not whether a divergence is justified. Consequently the deterministic audit engine verifies bookkeeping and evidence consistency while human/AI methodological review challenges substantive completeness.

## Catalog integrity

The WCAG inventory was derived from success-criterion sections of the official WCAG 2.2 HTML and filtered to A/AA, yielding 55 unique identifiers. Each is represented separately, alongside 45 original UX criteria. Native applicability is an audit decision, not deletion of the baseline list. Check that all records have stable IDs, dimension, kind, question, method, pass condition, countercheck, recommendation and source. Standard summaries are navigation aids: exact definitions and exceptions remain authoritative.
